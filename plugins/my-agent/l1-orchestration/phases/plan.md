## 2B Plan Review

1. Record: `python3 "${CLAUDE_PLUGIN_ROOT}/l4-tools-guards/scripts/run-log.py" step n=2B name=Plan-Review --model <main session model ID> --data-dir "<data folder>" --task-dir "<task_dir>"`
2. **Plan gaps:** run `python3 "${CLAUDE_PLUGIN_ROOT}/l4-tools-guards/scripts/plan-lint.py" --task "<absolute task folder>"`, also when Plan Review is skipped. Each `plan-lint: FAIL <gap>` line is fixed before anything else, like a BLOCKER in item 4 (a missing check tag in a confirmed `scope.md` is an L1 edit there; record `fix what="Plan gaps <gap>"`), then run it again until `plan-lint: ok`. It is not a Plan Review round. The G1-B hook runs the same check and denies the `Approved` line while a gap is left. Whether to skip Plan Review follows the profile file. If skipped, write `SKIPPED <reason>` in `plan-review.md`.
3. Hand it to `my-agent:plan-reviewer`. Pass: the paths of `plan.md`, `intake.md`, `explore.md`, the same `agent-models.py show` lines as for architect, and the result path `plan-review.md`. Do not pass architect's explanation.
4. Handle the judgment the same way in every profile. "Small" is the SKILL.md level-table size (2 task files or fewer, about 10 lines); a finding that turns out larger goes to architect.
   - **L1 edit of `plan.md`** (small): archive per "Rewrite before approval" below, edit `plan.md` with Edit (SKILL.md "Tool choice"), then record `python3 "${CLAUDE_PLUGIN_ROOT}/l4-tools-guards/scripts/run-log.py" fix what="Plan Review <severity> <path>:<line>" files=plan.md before=G1-B archive=<archive folder> --data-dir "<data folder>" --task-dir "<task_dir>"`. **Architect rewrite** (larger): archive and write the `revision … before=G1-B` line as in that section, then pass the `plan-review.md` path to architect.
   - The **findings list table**, after every judgment (`READY FOR APPROVAL` and `REVISE` alike, every round), also when no finding needs the person, and before any fix or popup: show all its findings in the chat, one row per finding: `# | Severity | Location | Finding | Fix L1 would apply | Who decides` (not the count table of gates.md "Gate reports"). `Who decides` is `L1 applies` for an unmarked finding and `you decide` for a marked (`[ask person]`) one. A judgment with no findings gets the one line `Plan Review Run <n>: no findings.` instead of a table.
   - `REVISE` (any BLOCKER): the marked-findings popup below comes first, so the fix holds the answers; then small → L1 edit, otherwise architect rewrite; then judge again. If the third `REVISE` comes, show that judgment in the G1-B popup and leave it to the person, even while delegated approval is on (SKILL.md "Delegated approval"; the popup is unchanged).
   - `READY FOR APPROVAL`: never another Plan Review round. Handle the findings below, then go to G1-B.
     - Unmarked SHOULD-FIX and NITPICK, `READY` and `REVISE` alike: apply them without a popup (L1 edit if small, else architect).
     - Marked findings (`[ask person]`, any severity): after the findings list table above (not shown twice), ask one popup that lists them, recorded with `ask gate=Q … rec="Apply all"` and `answer gate=Q`. The question keeps the several-part layout of SKILL.md "Question rules", with the SHOULD-FIX line (a problem worth fixing that does not block the gate) when one is listed, one plain line that these findings change the scope or need your answer, and `- Next:` last. Choices: `Apply all (Recommended)` / `Approve without applying` / `Pick myself`. They skip only SHOULD-FIX and NITPICK items; a BLOCKER is always fixed (the judge's fix, or the Other field text). No marked finding: no popup. Delegated approval answers `Apply all`.
   - L1 writes the `## Decisions` lines in `plan-review.md`; architect does not write that file. Each applied or declined item is one line in `## Decisions`: `- <severity> <path>:<line> <summary> → applied by L1 | applied by architect | declined`.

- Do not ask the kind. Before handing it back to architect, archive to `archive/<time>-rev<current rev>-draft/` and write a `revision rev=<current rev> before=G1-B why=… archive=…` line (an L1 edit: the variant below). The rev does not go up, and nothing is written to `## Revisions`. If the request changes the confirmed scope (`scope.md`), it is `Revise this task` in `changes.md` "In-flight revision".

A NITPICK that turns out larger goes to architect.
