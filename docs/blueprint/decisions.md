# Decisions

## Constraints
- The write guard is not weakened by the notes feature: the coder writes nothing in the task folder and only L1 stores notes (261117-notepads-learnings-handoff)
- Add no new gate, and no new popup kind or question beyond those named here. A non-gate popup after Intake whose answer is settled is answered by L1 with the recommended choice; the questions added to a task are the scope-width popup that opens the Scope interview and, on an exception path, the plan-finding popup for `[plan]` review findings, and the marked-findings popup replaces the Scope Review and Plan Review findings popup, so no other question is added — the person decided this at Scope; architecture 4.1 principle 6; revised by 261126-plan-finding-route (261126-plan-finding-route)
- A scope or plan judgment file written before the marks (no `[ask person]` on its findings) is read and counted as before, and the mark does not change the `(severity, location)` of a finding; the handling of BLOCKER findings and of the rounds of a `REVISE` judgment (fix, judge again, third `REVISE` to the person) does not change (261124-retro-items-0291)
- Add no new agent and no new run-log line kind (261117-notepads-learnings-handoff)
- SKILL.md stays under 15,000 characters and each rule file L1 reads at once stays under 15,000 characters — tests enforce this; raised from 12,700 on 2026-11-27 (earlier from 12,500 and 11,500) because rules are placed in the file whose purpose they serve, not by the room left; 15,000 characters is about 6,465 tokens at 2.32 characters per token on Codex and about 5,769 at 2.6 on Opus 5.5, so a file at the limit does not fit a 5,000-token read; the person chose the limit (261127-accept-speedup)
- The allow list of agents that always pass before G1-B approval (`BEFORE_APPROVAL`: explorer, scope-reviewer, architect, plan-reviewer) does not grow; the researcher and the writer pass only under their own conditions (261124-background-research-q45)
- Existing behavior for tasks without a `## Background research` section does not change (261124-background-research-q45)
- Runtime rules carry no temporary exception or workaround wording; the architecture document changes in the same commit so the runtime works as designed (261117-notepads-learnings-handoff)
- The worker turn limit, the "a stopped worker is retried once, then E" handling and the E conditions do not change (261117-notepads-learnings-handoff)
- Judge agents receive only paths and criteria (261117-notepads-learnings-handoff)
- Text in the repository is English. Only the Korean README and the Korean feature overview page are exceptions (261117-notepads-learnings-handoff)
- A release puts the feature and the version-location changes in one commit (261117-notepads-learnings-handoff)
- Steps show as phase digit plus a letter restarting in each phase: ① A Intake, B Explore → Scope; ② A Plan, B Plan Review; ③ A Execute, B Merge; ④ A Verify, B Review → Deliver (`1A`…`4B`); phases keep their numeric ①–④ display and step names are not renamed — the person chose this scheme at Scope (261120-tray-step-letters)
- The step IDs (`1A` Intake, `1B` Explore → Scope with Background research inside it, `2A` Plan, `2B` Plan Review, `3A` Execute, `3B` Merge, `4A` Verify, `4B` Review → Deliver) are used in run-log step lines, rule-file headings and references, the design doc and the generated architecture page, the scripts and their tests; the letter scheme, the ①–④ phase display and the step names do not change; old run-log step lines carry only the numbers 1–8 and stay readable, also in a log that mixes old and new lines; old task records are not rewritten (261125-reduce-l1-cost)
- The gates are named `G1-A` and `G1-B` everywhere (rules, popups, run-log lines, scripts, hooks, monitor, tray, documents, tests); G2, G3, E keep their names; run-logs written with `G1a`/`G1b` are still read as `G1-A`/`G1-B` (`ma_schema.gate_name`, legacy map), and `run-log.py` writes only the new names; dated maintenance notes, the old plan documents, probe records, old-format monitor fixtures and `docs/agent/` keep the old names as history (261125-reduce-l1-cost)
- The letter tables (web `STEP_CODE`, Swift `stepCodes`, architecture template `STEP_CODE`) are explicit literals, not a formula, and are changed together with the name tables (web `STEP_NAME`, Swift `stepNames`); tests compare them — duplicated surfaces must not drift (261120-tray-step-letters)
- G2 (the permission dialog before a risky tool call, such as the commit) and E (the escalation popup) always go to the person, also under delegated approval; a BLOCKER is still fixed before G3 (261120-g3-findings-auto)
- No gate starts the monitor: with the monitor off, the gate reports are read in the chat and the report pointer line gives the task folder — the person chose this with the monitor default (261120-g3-findings-auto)
- The run-log line kinds and their fields stay as they are, so existing task records stay readable by the tally, the monitor and the tray app (261120-g3-findings-auto)
- A monitor settings file with an explicit autostart or report-open value behaves as before (261120-g3-findings-auto)
- The report fields the Phase timeline has (`timeline.end`, `steps[].n/name/start`, `backs[].from/to/at/why`) keep their meaning; only new fields are added, and existing task records show correctly without being rewritten (261122-timeline-back-labels)
- Gate marks (G1-A, G1-B, G3), the row order and the bar colors of the Phase timeline do not change, and every new monitor UI string has an English and a Korean form (261122-timeline-back-labels)
- No behaviour of the plugin changes in a test cleanup: the blueprint language rule is the only runtime change of 261122-prune-tests-blueprint-en, the capability table file `tools/codex-probe/capabilities.json` stays because the design document cites it, and a test removed as a duplicate names the remaining test that asserts the same thing (261122-prune-tests-blueprint-en)
- The behavior of the git guard is written in the architecture document (4.4, 4.12, and 4.6 for `Cd`) before the code, and the code does nothing outside it; no temporary exception or workaround wording in the runtime rules (261122-harden-g2-deny-rules)
- A crash of `git-guard.py` blocks the call (exit 2), like the other gate hooks (261122-harden-g2-deny-rules)
- No settings file under `~/.claude` is edited by a task, so a rule the person merged by hand before 0.26.0 stays until the person removes it; the 16 Bash deny patterns of the old list are gone from `permissions.json` and `git-guard.py` acts in their place during a task (261123-policy-scope-review)
- `*.key` stays denied by name, and no pattern deny rule is written to match `--force-with-lease` (261122-harden-g2-deny-rules)
- The G1-A, G1-B and G3 approvals stay popups, G2 and E always go to the person, and every Intake popup (running task, flags, profile, committing the task log, the git check, the model preset) is asked every time and never answered by L1; Intake has no task-location popup — revised by 261126-popup-intake-cdguard (261126-popup-intake-cdguard)
- The blueprint keep-or-change popup keeps its two choices, `Keep it` and `Change it`, and its place in the Explore step; the settled-popup and delegated-approval rules were not changed for it (261126-popup-intake-cdguard)
- Only the build step of a dev task, or the first `worktree.py create` of another profile, adds or takes over the `Cd(...)` rule; `cd-guard.py` creates a missing settings file and keeps it out of git, leaves an invalid settings file unchanged with one line and an error exit, does nothing on Windows, keeps its record format (the settings file and the rule), and the rule is removed on the same paths as before, now through `worktree.py cleanup`, which runs `cd-guard.py --remove` first — the guard's other behaviour was a hard constraint of the take-over change 261126-popup-intake-cdguard; the removal through `worktree.py cleanup` was added by 261126-parallel-coder-copies (261126-parallel-coder-copies)
- The feedback file in the data folder changes only through the feedback script, and the person sees the closings before they run (261122-triage-open-feedback)
- A size cut of an agent definition never drops a rule: a rule is moved, merged with an identical one or reworded shorter with the same meaning, and a reason is dropped only when the agent's action stays the same; each cut is listed in a record next to the place or code that still states it (261122-reduce-agent-prompt-size)
- Each L2 definition keeps a General, a Research and a Dev section, and the headings, profile headings and verdict lines that tests, scripts and the architecture page generator read stay as they are (261122-reduce-agent-prompt-size)

- Only the architect gets the Edit tool and the scope-guard refusal for unresolvable plan changes applies to the architect's plan file only; other L2 agents, L3 agents and L1 are judged as before, and a Write of the whole plan is judged as before (261122-architect-edit-tool)
- Who changes the plan does not change: a small change before approval is an L1 edit (2 task files or fewer, about 10 lines), anything else goes back to the architect; only L1 writes the approval line and the `Prototype: requested` line, and the `## Revisions` lines stay as they are (261122-architect-edit-tool)
- The architect definition stays at or under 10,981 decoded characters, pinned by `test_architect_edit_rule_and_size` (261122-architect-edit-tool)
- `task-log-copy.py` copies the `.gitignore` before the task folder, so the copied log never shows as untracked; a failed copy removes what the run created instead of reordering, and never touches a `.gitignore` or folder that existed before (261123-review-task-log-copy)
- The Background-research timeline label is not a new entry of the step letter and step name tables (web, menu bar app, architecture template), which stay as they are (261124-monitor-background-research)
- Existing changed-file maps and review files written before the criterion tag keep working: a map without `## Findings` and a review without tags are valid input (261124-review-findings-rejudge)
- The rule that a rerun runs each full test suite once is not changed by the findings re-judge (261124-review-findings-rejudge)
- The L1 phase file `accept.md` and the skill file are not enlarged past the 15,000-character limit for the findings re-judge; `SKILL.md` is not touched — limit raised from 12,700 by 261127-accept-speedup (261127-accept-speedup)
- The popup explanation lines add no popup, gate or choice to G1-A, G1-B or G3, and keep the popup layout (short question first, one `- ` line per part, `- Next:` last); the remote take is offered only under its stated condition (261124-retro-items-0290)
- The rules never remove a harness lock on a worktree (no `git worktree unlock`) (261124-retro-items-0290)
- The writer joins the before-approval allow list only under its own conditions (the prototype, and the G1-B gate report); G2 and E always go to the person; the small-fix path after a Review BLOCKER does not change for unmarked findings (a `[plan]` BLOCKER gets the plan-finding popup before any fix), and the delegated G3 cap of 3 and the E rules do not change; the gate reports still work with the monitor off and the report-open setting and its default do not change — the small-fix clause revised by 261126-plan-finding-route (261126-plan-finding-route)
- A `review.md` written without the `[plan]` mark is read as before, a line without the mark in its stated place is unmarked, and the mark changes neither the criterion tag, the `(severity, location)` of a finding nor the counts; no stored format other than the review finding line changes for it, and a round with no marked finding is handled as before (261126-plan-finding-route)
- Push only to the branch the person named for the task; `main` only with the person's explicit permission; no pull request unless asked; version tags are reported as local commands, not pushed (261125-reduce-l1-cost)
- Unit copies live under the task location's `.claude/worktrees/` as `my-agent-<task-id>-<unit>`, in git and non-git locations; creating, merging and removing them adds no branch, tag or commit and leaves the repository's branch, staging area and stash unchanged; a non-git location stays non-git (no repository folder, no ignore file, no branch check or commit), and its temporary store lives in the task's records folder (261126-parallel-coder-copies)
- The coder cannot change the temporary store or anything else in the task's records folder; read-only git commands stay allowed for a copy coder, and git's own refresh of a copy's index is not counted (261126-parallel-coder-copies)
- A kept unit copy is named to the person and its changes are never deleted or overwritten without telling; no harness lock on a worktree is removed (261126-parallel-coder-copies)
- The merge conflict rules stay: a small conflict is resolved by the orchestrator, a larger one reruns the later unit in the main tree, and two units changing the same code differently go to escalation (261126-parallel-coder-copies)
- What counts as evidence and how a criterion is judged do not change with the check record: PASS still needs cited evidence, a failing check command still fails its criterion, and the verifier falls back to running every check command itself whenever the record is stale, missing, has no fingerprint, or a summary does not match its log; the record never lowers the evidence bar (261127-accept-speedup)
- Only `check-commands.py` writes `checks.md` and `checks/`; the orchestrator never writes them by hand, and `verdict-fresh-check.py` (main session) and `scope-guard.py` (every `my-agent:` role) deny any write to them through one shared `ma_schema.RECORD_DENY`; a shell write whose target cannot be told passes, the stated limit (261127-accept-speedup)
- The check commands run one at a time, in order, in the script and in the verifier's fallback; the working-tree fingerprint always leaves out the task records folder `<task_dir>/<task-id>/`, and git-ignored files are not in it — an accepted limit the person chose (261127-accept-speedup)
- SHOULD-FIX and NITPICK items still go to the person at G3 when the judges run together; in a Verify FAIL round the coders fix the failed criteria and the review's BLOCKERs only (261127-accept-speedup)

## Non-goals
- The verifier does not judge quality findings; `[criterion none]` findings stay with the reviewer, which re-checks them against the previous review (261124-review-findings-rejudge)
- The small-fix path after a Review BLOCKER (L1 fixes, Review only reruns) is not changed for unmarked findings; a `[plan]` BLOCKER gets the plan-finding popup before any fix, also when the fix is small — the person chose it at Scope, revised by 261126-plan-finding-route (261126-plan-finding-route)
- The rules do not prevent or kill a background process a coder left, and the remote take is not detected by a trial or dry-run push (261124-retro-items-0290)
- No criterion tag on NITPICK lines of `review.md`; plan-review and scope-review findings carry no criterion tag (261124-review-findings-rejudge)
- The findings of the Review step at G3 are not auto-applied; the unmarked-findings rule covers Scope Review and Plan Review only (261124-retro-items-0291)
- The monitor's Status tab step list and its time sums (Background research time stays under step 1B there), the event log lines, the file list and the stopped-worker count are not changed for Background research; the menu bar app and the architecture page get no Background research display (261124-monitor-background-research)
- No Background research in the research profile (a sub-question structure that depends on a web fact is a `To confirm` item), for a small task of the dev and general profiles, or on the Codex host; no web research before G1-A; no separate approval popup for the questions, which are confirmed with the scope at G1-A — scope of Q45 (261124-background-research-q45)
- The four L3 definitions, the skill file and the L1 orchestration files are measured but not edited for size, and the survey's /compact advice is not adopted (261122-reduce-agent-prompt-size)
- The agent installers for Codex and Antigravity (`--install-agents`) are not run by a task; the person is told to run them (261122-reduce-agent-prompt-size)
- The git guard judges nothing outside a my-agent task, and it does not cover git aliases, scripts that call git, other tools (`gh`, MCP), a plain `$VAR` word in an option, refspec or pathspec slot, or a persistent `git config core.hooksPath` write; the documents state these limits (261123-policy-scope-review)
- No OS sandbox and no stopping of subprocess reads (`sh -c 'cat x.key'`); the READMEs only state the limit (261122-harden-g2-deny-rules)
- The blueprint script has no language check; a blueprint line in another language stays valid until the next update of its entry rewrites it (261122-prune-tests-blueprint-en)
- What the reviewer judges and the review file format change only as decided: the per-round `## Counts` table, the completeness of the first Review's listing, and the `[plan]` mark on findings whose fix needs a plan change — the person chose the mark at Scope, revised by 261126-plan-finding-route (261126-plan-finding-route)
- No writer for the G1-A report (L1 writes it and its Korean copy), no light path for SHOULD-FIX items, no new limit on what a later review round may raise, and no change to the text of the G2 permission dialog (261125-reduce-l1-cost)
- Nothing is pushed, commits or tags, under delegated approval (261120-g3-findings-auto)
- The report-open setting and its default are not changed (261120-g3-findings-auto)
- The tray mini window List shows no step text and no phase display; the Windows tray is not changed — placeholder only, and not part of the request (261120-tray-step-letters)
- The status colors and the 8-cell progress bar are not changed; no letters for gates and no renaming of steps or phases — out of the request (261120-tray-step-letters)
- No notes for researcher and writer work units — only handoff between coder units is covered (261117-notepads-learnings-handoff)
- The coder does not write notes itself during work, and no note survives when a unit stops at the turn limit — this keeps the write guard (261117-notepads-learnings-handoff)
- Notes are not shown in the monitor or the Report tab (261117-notepads-learnings-handoff)
- Notes are not used for the blueprint update or the retrospective (261117-notepads-learnings-handoff)
- The repository does not name other tools or their features (261117-notepads-learnings-handoff)
- The write guard does not judge the contents of a script file that an interpreter runs; only inline code on the command line or in a heredoc is read, and the design document and the guard's description state the limit (261122-triage-open-feedback)
- The guard does not work out the text after an Antigravity `multi_replace_file_content` call from its parts; the call is refused instead (261122-architect-edit-tool)
- "Back to Execute" adds no work unit and still only reruns existing ones; a new work unit is reached through `Revise this task` (261126-plan-finding-route)
- The monitor gets no display for the `[plan]` mark beyond showing the finding's text — the person chose it at Scope (261126-plan-finding-route)
- The other ways the `Cd(...)` rule can be left behind (a task never continued, an abort cut off halfway, restarting as or splitting into a new task, a damaged record, a moved project folder) get no separate fix, and two running tasks sharing one settings file get no extra handling (the first to end removes the rule); except after a folder move, where the rule with the old path stays, the next dev task in the same location takes the rule over and removes it when it ends — the person chose it at Scope (261126-popup-intake-cdguard)
- Unit copies are not made on Codex and Antigravity, which keep running coder units one after another (261126-parallel-coder-copies)
- No start-point check at intake and no branch cleanup after a push; unit copies get no work branch. The Intake work branch is the one exception: after `Fix it first` for `main`, `master` or a detached HEAD, `intake.py work-branch` creates and switches to `my-agent-task/<task-id>` — revised by 261127-accept-speedup (261127-accept-speedup)
- No fixed exclude list, and no creating or editing of the user's ignore files; a non-git copy leaves out only what the `.gitignore` files inside the folder exclude, plus the records folder and the copies folder (261126-parallel-coder-copies)
- The plan-finding route does not change Verify FAIL handling, the E conditions or a change request the person types — it covers marked review findings (261126-plan-finding-route)
- Check commands are not run at the same time, and no reviewer judge fixtures exist (only two verifier fixtures were added); the reviewer's and verifier's judgments and file formats change only by the `(checks.md)` mark, the record citation and the `- <command> → covered by <full suite command>` line (261127-accept-speedup)

## Decisions
- Background research (decision Q45): web research before the plan is allowed only for at most 4 questions (`b1` to `b4`) that L1 writes in the scope under `## Background research` and the person confirms with the scope at G1-A; the rule "before approval, delegate only what the person allowed" (Q6) stays, with the approval point for these questions moved to G1-A; the notes under `background/` are architect input and a choice resting on one is marked `(background b<n>)`; a note that contradicts the scope reopens G1-A with `Revise`; a `Not found` question becomes `To confirm` — architecture document Q45 (261124-background-research-q45)
- Before plan approval the hook passes a researcher only when the profile is not research, the scope has a `Confirmed ` line under `## Confirmation` and a `## Background research` section, the prompt has a `Background question: b<n>` line and that `b<n>` is listed; the write guard limits the researcher to `background/` before approval and to `work/` and `background/` after it; the run log carries `unit=b<n>` (261124-background-research-q45)
- The plan lint and the G1-B hook enforce in code that a `(background b<n>)` mark names a question of the scope (draft marked this lint optional; made required so the mark format is enforced); the plan-reviewer judges only whether the claim behind a mark is in the notes (261124-background-research-q45)
- A size limit is raised only when a file of its class is over it after the change, to the largest such file's size rounded up to the next 100, counted in decoded characters; `test_antigravity.py` keeps 11,500 for `hosts-antigravity.md`; the architect definition keeps its 10,981 pin and existing text is shortened without dropping a rule when new rules do not fit (261124-background-research-q45)
- scope-guard refuses an architect change to its own plan file when it cannot work out the text after the change (no replacement text reaches the guard, empty text, text not in the file exactly as given, or in the file more than once without `replace_all` being exactly true); the architect changes an existing plan with Edit and writes with Write only the first draft or a full rewrite; the person chose version 0.25.2 at Scope; architecture 4.12 (261122-architect-edit-tool)
- Handoff between work units: L1 stores the notes part of the coder final report in the single file `coder-notes.md` in the task folder and passes its path only to later coder calls. Alternatives not taken: the coder writing the file itself (conflicts with the write guard, and a worktree coder cannot write to the task folder), one notes file per unit — architecture document Q31 (261117-notepads-learnings-handoff)
- Notes are written and read during the task. This differs from the blueprint and the retrospective, which are written after the task ends (261117-notepads-learnings-handoff)
- The notes part is stored up to 10 lines not counting blank lines; beyond that, the first 10 lines and one truncation line are stored. Notes are treated as data, and the plan wins when it conflicts with a note (261117-notepads-learnings-handoff)
- Coder units run through a workflow also have the script return the notes part together with the first line, and L1 stores it by the same rule — applied from plan-review SHOULD-FIX (261117-notepads-learnings-handoff)
- Like the other records in the task folder, the notes file is kept with the task folder and is not deleted during a revision; entries are told apart by the rev number in their label (261117-notepads-learnings-handoff)
- Inside a step circle under a phase heading (web Dashboard and replay step lists, architecture page rail and step cards) the letter shows alone (`A`); standalone text shows the full label (`3A Execute`); a step outside 1–8 shows its raw number — chosen at Plan Review (261120-tray-step-letters)
- The monitor API keeps `step` as the index 1–8, read from both forms of run-log step line through `ma_schema.step_index`, so the display tables (`STEP_CODE`, `stepCodes`) stay; the gate tally prints the lettered label (`3A Execute`) for old and new lines — chosen at Plan Review, revised by 261125-reduce-l1-cost (261125-reduce-l1-cost)
- The feature pages' walkthrough nodes keep the phase digit (two nodes per phase show the same digit); only the phase and step sentence uses the letters — chosen at Plan Review (261120-tray-step-letters)
- Every plugin version raise adds a new entry at the start of the architecture document status line, and `test_arch_doc` pins it (now `v0.72`, plugin 0.25.2) — Scope change at Execute (261120-tray-step-letters)
- Under delegated approval L1 answers G3: `Rework: fix all open items` while a SHOULD-FIX or NITPICK item is open, the take choice when none is; the G3 fix loop is capped at 3 rounds, then E — the person chose 3 at Scope; architecture document Q39 (261120-g3-findings-auto)
- An open risk at G3 does not stop L1's take under delegated approval; L1 lists the open risks in the chat — the person chose this at Scope (261120-g3-findings-auto)
- The monitor's `autostart` is off by default: only JSON `true` starts it at task start or resume and at the tray app's start; the monitor skill and Open Monitor always start it; broken JSON or any other value counts as no value — architecture document Q40 (261120-g3-findings-auto)
- The findings table (`Severity | Found | Fixed | Open`) and the popup layout apply to every gate approval (G1-A, G1-B, G3), not only G3 — the person asked for this during Scope Review (261120-g3-findings-auto)
- The counts of `findings.py` and of the Report tab come from the same functions in `ma_schema` (`review_state`, `judged_counts`), so the two cannot drift — applied from plan-review (261120-g3-findings-auto)
- The Report tab's legend for a G3 answered by L1 is English-only, like the existing wait legend — applied from plan-review NITPICK (261120-g3-findings-auto)
- scope-guard takes a worktree as the coder's own only when its folder is `agent-<agent_id>`, or a unit copy that the coder's prompt names on its second line (`Worktree: <path>`) while that unit is in `running`; a coder whose `cwd` is another coder's worktree (a moved session) has the main-tree rules, and relative paths still resolve against that `cwd` — the person asked for it after two tasks where the session's folder moved; the `agent-<agent_id>` rule is from direct-261120-worktree-scope-guard, unit copies were added by 261126-parallel-coder-copies (261126-parallel-coder-copies)
- In the dev profile L1 checks the session's folder (`git rev-parse --show-toplevel`) before every main-tree hand-out and before 3B Merge; on a mismatch the person is asked, also under delegated approval, because L1 cannot move the session — retrospective proposal 3 of 261120-g3-findings-auto (direct-261120-session-folder-check)
- The session is kept out of every folder under the task location's `.claude/worktrees/` (unit copies, harness agent worktrees, task worktrees) by a `Cd(...)` deny rule that `cd-guard.py` adds to the task location's `.claude/settings.local.json` at the start of Execute (dev profile) or before the first unit copy is created (other profiles) and removes when the task ends, on every path that deletes `.active` (Accept, Commit, every Abort, the `continue` close); a rule already there that the task has not recorded is taken over (recorded as the task's own, with a line saying it is removed when the task ends); only the exact rule recorded in `cd-guard.json` is removed, every copy of it, all other entries and settings stay, and a rule written differently by even one character is neither taken over nor removed; a rule the person added that is exactly the same as the guard's is no longer kept after a dev task ends, and the rule does not outlast the task — the person chose "remove it when the task ends" at the Scope of 261123-policy-scope-review, whatever verdict the review gave it, and chose the take-over at the Scope of 261126-popup-intake-cdguard; Claude Code 2.1.330 may print "Deny rule Cd(...) matches no tool" at startup, which a probe showed is harmless: a typed `/cd` into an `agent-*` folder is refused — revised by 261126-popup-intake-cdguard and widened to the whole copies folder by 261126-parallel-coder-copies (261126-parallel-coder-copies)
